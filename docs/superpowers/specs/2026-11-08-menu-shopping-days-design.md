# 买什么：采购按「用餐天数」估算（设计）

> 日期：2026-11-08
> 范围：`/api/ai/menu` + 买什么页（`/dishes`）
> 状态：已批准并实施（采购分组固定五类 + 「其他」兜底；天数默认 1）

## 要解决的问题

现在的采购清单是**一餐的量**：3 人输入后，输出「鸡腿 x3只（约600g）、冬瓜 x400g」。但真实的使用场景是「去超市把一周的菜买回来」，一餐的量没有意义。

根因不在数字，而在**采购清单的组织方式**：现在是「按菜汇总」，而真实买菜是「按食材给总量、按品类和保质期分组」。一个人不会想「菜 A 要 2 个番茄、菜 B 要 3 个番茄」，而是「番茄一共买 5 个」。

## 目标 / 非目标

**目标**

1. 菜单页新增「吃几天」（1~7，整数，硬上限）
2. 菜单覆盖这几天（约 `天数 × 3` 道，不按天排）
3. 采购清单改为**按品类分组 + 按 `人数 × 天数` 的总量**，易坏/耐存分别注明

**非目标（明确不做）**

- ❌ 不按天排菜单（「Day1 早/中/晚」）——真实买菜是买一批、每天看冰箱决定，硬排到天反而打乱计划
- ❌ 不估价格、不算营养总量
- ❌ 不做保质期精确计算（只在文字里提示「建议先吃」「可冷冻」）
- ❌ 天数不持久化到设置（每次手动填，默认 1）

## 方案

### 已排除的两个方案

| 方案 | 为什么不选 |
| --- | --- |
| 只加「天数」，菜单仍是一餐 | 菜单与采购脱节：看到 4 道菜却要买 7 天的量，逻辑不自洽 |
| 每道菜带食材用量、服务端精确汇总 | 数学最准，但 7 天 21 道 × 8 个食材 ≈ 170 条 JSON，结构化输出失败率与耗时都会显著上升，不划算 |

### 选定方案

**参数**（`POST /api/ai/menu`）

```ts
{ people: number;      // 必填，1~50（不变）
  days?: number;       // 新增：用餐天数，整数 1~7，缺省 1
  preference?: string } // 不变
```

**菜单规模**

| 天数 | 菜数指引 |
| --- | --- |
| 1 | 沿用现有规则（`people ≥ 4` 时「建议菜数不少于 N 道」）——**保证 days=1 行为零变化** |
| 2~7 | `建议菜数约 ${min(days*3, 21)} 道，覆盖 N 天` |

**采购清单结构变化**

```ts
// 改前
shopping: string[]                       // ["鸡腿 x3只（约600g）", "冬瓜 x400g"]

// 改后
shopping: { group: string; items: string[] }[]
// [{ group: "肉禽蛋", items: ["五花肉 1.5kg（耐存：分装冷冻）", ...] }, { group: "蔬菜", ... }]
```

**解析容错（关键）**：schema 用 `z.union` 同时接受旧的扁平数组，扁平数组自动归一化为单组「采购清单」。这样模型偶尔退回旧格式也不会触发重试/502。

```ts
shopping: z.union([
  z.array(z.string()).transform(items => (items.length ? [{ group: '采购清单', items }] : [])),
  z.array(z.object({ group: z.string().min(1), items: z.array(z.string()) }).strict()),
])
```

**采购提示词要点**（给基准，不让模型瞎猜）

```
按 N 人 D 天估算采购总量：
- 肉禽鱼 150~200g/人/天；蔬菜 300~500g/人/天；蛋 1 个/人/天；主食 200~300g/人/天
- 按品类分组（肉禽蛋 / 蔬菜 / 豆制品 / 主食 / 调料）
- 用量折算成好买的单位（斤/把/盒/袋），四舍五入到整数
- 易坏食材注明「建议 2~3 天内先吃」，耐存食材注明「可冷冻/久放」
- 调料只列需要补货的，不要罗列每家都有的盐糖油
```

**前端（买什么页）**

- 人数下方加「吃几天」输入（`type=number`，`min=1 max=7 step=1`）
- 校验与服务端同口径：非 1~7 整数 → 行内提示，不发请求
- 「采购建议」区块改为分组渲染（每组一个小标题 + 列表）
- 区块内加一行口径说明：「按 3 人 7 天估算，实际按家里存量和饭量调整」

## 可行性验证（已实测，非估算）

直接调上游验证「7 天菜单 + 分组采购」这一最坏情况：

```
3人1天  → 8.0 秒,  2421 bytes
3人7天  → 35.9 秒, 9837 bytes（约 3.5k tokens），20 道菜 / 5 个采购分组 / 36 条目
输出 JSON 一次解析成功
示例：{"group":"肉禽蛋","items":["五花肉 1.5kg（耐存：切小块分装冷冻，可放 1 个月）", ...]}
```

**结论：120 秒超时不是问题**。最坏情况 36 秒；即便触发「解析失败重试一次」，2×36 = 72 秒 < 120 秒，不需要改 `ai-client` 的超时配置。

## 风险

| 风险 | 评估与处理 |
| --- | --- |
| 上游 `max_tokens` 截断导致 JSON 不完整 | 实测 7 天 3506 completion tokens 成功；若供应商默认上限偏低可能截断。**处理**：失败走既有「重试一次」，仍失败给 502 中文提示（已有机制，不新增） |
| 天数越大，菜名重复/凑数 | 菜数按 `天数×3` 封顶 21，避免 21+ 道时质量下降；灵感种子仍按请求随机 |
| 采购量估算不准 | 给人均日消耗基准显著改善，但仍非精确值。**处理**：UI 显示估算口径，避免用户当成精确值 |
| `shopping` 结构变更影响既有代码 | 前端 + 测试同步更新；解析层同时兼容扁平数组，旧格式不会 502 |
| days=1 行为被改坏 | 提示词分支严格区分：days=1 沿用原文案；补一条回归测试锁定 |
