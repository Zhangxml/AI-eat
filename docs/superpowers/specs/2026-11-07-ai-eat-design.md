# AI-eat（AI 菜谱工具）设计文档

> 日期：2026-11-07
> 状态：已批准（2026-11-07 用户确认）
> 代码位置：`~/tools/AI-eat`（当前目录，全新项目）

---

## 1. 意图与背景

给用户自己用的 AI 菜谱工具。解决两个真实场景：

1. **冰箱剩菜不知道做什么**：告诉 AI 现有食材，生成可执行的菜谱；
2. **准备买菜 / 点菜**：随机推荐一桌多人菜单（"点菜"），并附采购搭配建议。

核心形态：**对话式聊天为主**，AI 生成的菜谱可一键保存到**服务端文件菜谱库**；同时支持人工录入菜谱兜底。手机浏览器访问，局域网服务器部署。

## 2. 目标 / 非目标 / 反目标

### 目标

- 手机浏览器打开即可用，响应式适配，简洁工具风
- 对话式交互：AI 按食材生成菜谱、随机点菜（多人菜单 + 采购建议）
- 个人菜谱库：AI 生成 / 人工录入的菜谱统一入库，**存服务端项目目录**（浏览器清缓存不丢数据，多设备共享同一份库）
- 按食材搜索已有菜谱
- 营养 / 热量分析（AI 估算，标注为估算值）
- 数据备份：`data/` 目录直接可备份 + 页面内导出/导入 JSON
- 部署形态与用户已有的 LibreTV 一致：局域网服务器，手机直连 `http://服务器IP:端口`

### 非目标（本期不做）

- 多用户 / 注册登录体系
- PWA 安装到桌面（响应式网页即可）
- 做菜特殊交互（屏幕常亮、大字模式、语音朗读、免触摸翻页）
- 拍照识别食材、语音交互
- 独立购物清单功能（采购建议作为点菜输出附带）
- 联网核实 AI 菜谱真实性（用固定 JSON 模板约束输出即可）
- 聊天记录持久化（已确认：刷新页面/换设备对话即丢，有价值的菜谱入库即可）

### 反目标（出现即为失败）

- 数据存浏览器本地导致菜谱库丢失（用户明确否定过该方案）
- 手机上排版错乱、需要横向滚动
- AI 输出格式随机的自由文本，无法入库（必须结构化）

## 3. 约束

- 单人自用，部署在家庭/办公局域网，纯 HTTP 直连 IP
- AI 供应商：DeepSeek、智谱 GLM，均按 OpenAI 兼容接口接入，可配置切换
- 成本敏感：普通对话/生成用模型默认档位即可，不做多模型级联
- 用户没有指定验收标准，以"两个核心场景能顺畅走通"为准

## 4. 方案对比（已拍板：方案一）

### 方案一：Next.js 全栈单体（选定）

Next.js（App Router）+ React + TypeScript，API Routes 承担后端：AI 代理 + 菜谱库文件读写 + 静态托管，单进程单端口。

- 优点：一个项目一个进程；SSE 流式聊天在 Route Handler 中成熟；运维形态与用户已验证的 LibreTV 完全一致；前后端同语言同项目
- 代价：Next 框架对纯自用工具偏重（SSR 等能力冗余），接受

### 方案二：Vite React SPA + 轻量 Node 后端（Hono）（否决）

前端纯静态 + 约 200 行 Node 服务。

- 优点：最轻量、无框架魔法
- 否决理由：前后端两套脚手架需自行拼装；流式聊天、路由、鉴权全要手搓；在已确定需要服务端有状态存储（菜谱库）后，方案一的优势进一步扩大

## 5. 已决定的设计

### 5.1 技术栈

| 层 | 选型 |
| --- | --- |
| 框架 | Next.js 15（App Router）+ React + TypeScript |
| UI | Tailwind CSS，移动端优先响应式，简洁工具风 |
| 存储 | 服务端文件系统 `data/recipes/*.json`（一菜一文件） |
| AI | OpenAI 兼容接口，服务端代理，SSE 流式输出 |

### 5.2 AI 接入

环境变量配置（`.env` / compose），运行时可切换供应商：

```bash
AI_BASE_URL=https://api.deepseek.com   # 或 https://open.bigmodel.cn/api/paas/v4
AI_API_KEY=sk-xxx
AI_MODEL=deepseek-chat                 # 或 glm-4-flash 等
```

- 所有 AI 请求走服务端代理 `/api/ai/*`，API Key 不进浏览器
- 聊天流式输出用 SSE（`text/event-stream`）
- **SSE 事件协议（已拍板）**：`message` 事件推正文增量；菜谱生成完成时以 `recipe` 事件推送完整结构化 JSON；`done` 事件收尾。前端入库按钮直接使用已收到的 `recipe` 数据，**不二次调用 AI**（避免成本翻倍与内容不一致）
- **生成菜谱必须走结构化输出**：强制 JSON 模板（字段见 5.3），模型输出解析失败时重试一次，再失败则向用户报错而不是存入脏数据
- 菜谱可信度：不做联网核实，靠模板字段约束 + 用户自己判断（用户同意此取舍）
- **菜谱库上下文注入（已拍板）**：`/api/ai/chat` 与 `/api/ai/recipes` 调用模型前，读取菜谱库生成轻量摘要（每道菜仅名称 + 食材名列表）注入系统提示词，使 AI 能推荐库中已有菜而非重复生成；几十道菜规模下成本仅几百 token 级，可忽略
- **聊天记录不持久化**：对话历史仅存前端内存/组件状态，刷新即丢，服务端不存任何会话数据

### 5.3 菜谱数据模板（`data/recipes/<id>.json`）

```json
{
  "id": "r-1730000000-ab12cd",
  "name": "番茄炒蛋",
  "category": "荤菜",
  "servings": 2,
  "difficulty": "简单",
  "totalTimeMin": 20,
  "tags": ["家常菜", "快手菜"],
  "ingredients": [
    { "name": "番茄", "amount": "2个（约300g）" },
    { "name": "鸡蛋", "amount": "3个" }
  ],
  "steps": ["番茄切块……", "热锅下油……"],
  "nutrition": {
    "caloriesKcal": 180,
    "proteinG": 8,
    "fatG": 10,
    "carbG": 12,
    "estimated": true
  },
  "source": "ai",
  "createdAt": "2026-11-07T12:00:00.000Z",
  "updatedAt": "2026-11-07T12:00:00.000Z"
}
```

- `source`: `"ai" | "manual"` 区分来源；`nutrition.estimated` 恒为 true（AI 估算，非实测）；`category` 为可选字段（荤菜/素菜/汤/主食/其他），AI 生成必填，人工录入选填
- **营养字段人工录入时选填**（已拍板）：留空则详情页显示「未估算」；表单提供可选的「AI 估算」按钮补全；营养为空不影响列表展示与搜索
- 文件名即 id，用户可手动改文件，服务启动时容忍非法 JSON 文件（跳过并在列表接口返回警告，不崩溃）

### 5.4 API 设计

菜谱库 CRUD：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/recipes` | 列表（支持 `?q= 名称/食材搜索，?tag= 标签过滤） |
| GET | `/api/recipes/:id` | 详情 |
| POST | `/api/recipes` | 新建（人工录入或 AI 菜谱入库） |
| PUT | `/api/recipes/:id` | 编辑 |
| DELETE | `/api/recipes/:id` | 删除 |

AI 能力：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/ai/chat` | 对话主入口，SSE 流式；内部按意图路由（生成菜谱/点菜/自由问答） |
| POST | `/api/ai/recipes` | 按食材生成结构化菜谱 JSON（供前端"存入菜谱库"按钮使用） |
| POST | `/api/ai/menu` | 点菜：输入人数/口味偏好，返回菜名清单 + 搭配理由 + 采购建议（轻量，不含完整步骤）；用户对某道菜点「入库」时前端再调 `/api/ai/recipes` 单独生成完整菜谱 |

备份：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/backup` | 导出全部菜谱为单个 JSON |
| POST | `/api/backup` | 导入 JSON（按 id 去重，冲突时跳过并报告） |

#### 5.4.1 点菜页流程（已拍板：两段式）

1. 用户输入人数 + 口味偏好 → `/api/ai/menu` 一次调用返回**菜名清单 + 搭配理由 + 采购建议**（快，几秒内出结果）
2. 用户对菜单中某道菜点「生成菜谱并入库」→ 前端调 `/api/ai/recipes` 单独生成该菜的完整菜谱 → 展示结构化卡片 → 一键写入菜谱库

理由：一次生成 4~6 道菜的完整步骤又慢又贵，且用户通常只想要其中两三道；按需生成把成本和延迟都留给真正需要的菜。

### 5.5 页面结构

| 路由 | 内容 |
| --- | --- |
| `/` | 对话式主界面（聊天为主入口，菜谱卡片可在聊天中渲染并一键入库） |
| `/recipes` | 菜谱库列表（搜索框 + 标签筛选 + 按食材搜索） |
| `/recipes/[id]` | 菜谱详情（食材用量、步骤、营养估算，可编辑/删除） |
| `/recipes/new` | 人工录入表单 |
| `/dishes` | 点菜页（人数 + 偏好 → AI 菜单卡片 + 采购建议，可逐个入库） |
| `/settings` | 备份导出/导入、AI 供应商显示（只读，配置在环境变量） |

移动端布局：底部 Tab 导航（首页 / 菜谱库 / 点菜 / 设置），单列布局，触摸目标 ≥ 44px。

### 5.6 鉴权（借鉴 LibreTV 模式）

- 设置 `PASSWORD` 环境变量 → 启用简单口令登录，`POST /api/auth` 校验后发 httpOnly Cookie 会话
- Cookie `Secure` 标记按 `x-forwarded-proto` 推导（不依赖 `req.url`），纯 HTTP 局域网登录不受阻
- 不设置 `PASSWORD` → 无鉴权（局域网信任边界，自用默认推荐，省登录摩擦）
- 写接口（POST/PUT/DELETE/导入）与 AI 接口在启用口令后必须校验会话；GET 列表/详情同受保护

### 5.7 部署（照搬 LibreTV 形态）

- `run.sh`：`npm run build && nohup npm start`，启动后打印局域网地址
- `Dockerfile` + `docker-compose.yml`：端口映射到宿主机所有接口，`data/` 目录 volume 挂载持久化
- 监听所有网卡，手机浏览器 `http://服务器IP:端口` 直连，零配置

### 5.8 数据备份

- 首选：直接备份宿主机 `data/` 目录（compose volume 指向）
- 页面内：设置页导出/导入 JSON，用于手动迁移

## 6. 分阶段实施计划

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| 一：骨架+菜谱库 | Next.js 脚手架、Tailwind、移动端布局与底部导航、菜谱库 CRUD API + 文件存储、列表/详情/人工录入页 | 手机浏览器录入→查看→编辑→删除菜谱全流程可用，清浏览器缓存数据不丢 |
| 二：AI 接入 | AI 代理 + SSE 流式聊天、按食材生成菜谱（结构化输出）、聊天中一键入库 | 冰箱剩菜场景走通：输入食材→流式生成→入库→列表可见 |
| 三：点菜+搜索+营养 | 点菜页（多人菜单+采购建议）、按食材/名称搜索、营养估算字段贯通 | 买菜场景走通：输人数→出菜单+采购建议 |
| 四：收尾 | 导出/导入备份、PASSWORD 鉴权、run.sh + Docker 部署、暗色适配等打磨 | 局域网手机直连部署完成 |

每阶段结束可独立使用，阶段一即有实用价值（纯菜谱库）。

## 7. 留给建设者的部分

- 具体的意图路由实现方式（提示词设计、是否用 function calling / JSON mode，由建设者按所选模型能力决定）
- 聊天气泡中菜谱卡片的交互细节（展开/收起、入库按钮的确认方式）
- 加载/错误态文案、空状态设计
- SSE 断线重连策略（自用局域网环境，简单重试即可，不必过度设计）
- 文件写入的并发策略（单人使用，写临时文件+原子重命名即可，无需文件锁）

## 8. 用户明确否定过的方案（防止回潮）

- ❌ 菜谱数据存浏览器 IndexedDB / localStorage（清缓存丢失）
- ❌ PWA / 做菜特殊交互（常亮、语音、大字模式）
- ❌ 独立购物清单功能
- ❌ 多用户系统
