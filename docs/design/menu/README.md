# 模块：点菜·买什么（/api/ai/menu + 点菜页）

> 代码位置：`src/app/api/ai/menu/route.ts`（菜单生成）、`src/app/dishes/page.tsx`（点菜页）
> 消费方：导航「买什么」入口；复用 `/api/ai/recipes`（第二段按需生成）与 `RecipeCard`（展示/入库）

## 做什么

解决「准备买菜，不知道买什么、怎么搭配」：输入人数与**吃几天**（+可选口味偏好），AI 一次生成覆盖这几天的**菜单**（菜名+分类+推荐理由）与**按品类分组的采购清单**；对菜单中感兴趣的菜再按需生成完整菜谱入库。

导航入口命名「买什么」——比「点菜」更贴近该场景的真实意图（列采购清单）。

## 怎么做的

### 两段式流程（设计文档 5.4.1）

```
第一段（一次调用）：
  人数 + 天数 + 偏好 ──► POST /api/ai/menu
    ──► { dishes: [{name, category, reason}], shopping: [{group, items[]}] }
  渲染：菜卡列表（菜名/分类徽标/推荐理由）+ 采购建议区块（按品类分组）

第二段（按需，逐菜独立）：
  某菜「生成菜谱」按钮 ──► POST /api/ai/recipes { dish, servings } ──► { recipe }
  卡下方展开 RecipeCard ──► 「存入菜谱库」（toDraft 剥离+防抖，同聊天页模式）
```

### 推荐依据（四路输入）

`buildUserMessage` 拼装（route.ts）：

> 入参：`{ people: 1~50, days?: 1~7（缺省 1）, preference?: ≤500 字 }`

1. **人数 + 天数**：days=1（缺省）时 `今天 N 人吃饭`，people≥4 附加「建议菜数不少于 N 道」（份量级启发，与改造前完全一致）；days≥2 时 `今天 N 人吃饭，要买 D 天的菜` + 「建议菜数约 min(D×3, 21) 道，覆盖这 D 天（不必按天排列）」
2. **口味偏好**：自由文本原文透传（「清淡、孩子吃、不吃香菜」都有效）
3. **菜谱库摘要**：系统提示词注入（同聊天模块），仅用于避免与库中完全相同的重复菜，不再优先已有菜
4. **固定搭配规则 + 风格档位**（档位来自全局设置 `/api/settings`，请求体不再接收 style）：「注意荤素搭配」+ 按档位取约束——home（默认）「经典家常菜为主，简单好吃下饭」、creative「避免大路菜，优先中式地方风味」；每请求按档位随机「技法 + 风味」灵感（home 用家常池、creative 用中式地方池，**已移除异国风味**）；菜单温度 0.8

### 采购清单：按「人数 × 天数」估总量

| days | 采购口径 |
| --- | --- |
| 1（缺省） | 每道菜所需食材合并去重（量级与改造前一致）；输出同样按品类分组，仅展示结构统一 |
| 2~7 | 按 `人数 × 天数` 的总消耗估算，**按品类分组**，给人均日消耗基准（肉 150~200g、蔬菜 300~500g、蛋 1 个、主食 200~300g/人/天），用量折算成斤/把/盒/袋，易坏食材标注「建议几天内先吃」、耐存标注「可冷冻」 |

结构：`shopping: { group: string; items: string[] }[]`，`group` 取 `肉禽蛋/蔬菜/豆制品/主食/调料/其他`（与服务端 `SHOPPING_GROUPS` 同义，前端只做分组标题渲染）。

**解析容错**：

- `z.union` 同时接受旧的扁平字符串数组，自动归一化为单组「采购清单」——旧格式本身是合法输出，不该因结构差异浪费一次 AI 调用
- **同名分组自动合并**（保留首次出现顺序、items 拼接）：前端以 `group` 作 React key，同名分组会产生重复 key（reconciliation 异常 + 控制台告警），同一品类分散多处也不利于照着买
- 空 `items` 的分组被丢弃，不渲染空小标题

**格式规则位置**：`MENU_FORMAT_RULE` 与 `SHOPPING_GROUPS` 放在 `src/lib/ai-prompts.ts`（与 `RECIPE_FORMAT_RULE` 同址）。**不能放在 `route.ts`**——Next.js 只允许路由文件导出 HTTP 方法等固定符号，导出常量会触发 `.next/types` 的 `OmitWithTag` 约束报错（`tsc` 失败）。

**上限**：`days` 为 1~7 整数（`MAX_DAYS`），超出或非整数直接 400，**不静默收敛成 1**（避免用户以为买了 7 天的量）。该常量与点菜页表单位于 `src/lib/menu-form.ts`，前后端共用一份。

**口径说明**：UI 在采购区块顶部标注「按 N 人 D 天估算，实际按家里存量和饭量调整」，避免用户把估算当成精确用量。

输出协议：`<menu>{JSON}</menu>`（复用 ai-prompts 的平衡扫描解析）+ zod schema（dishes 的 category 五枚举、name/reason 非空；shopping 为 `{group, items[]}[]`，并兼容旧的扁平字符串数组）。失败重试一次同 AI 模块公共协议。

### 并发：点菜 vs 逐菜生成

两段式天然允许「菜单 A 的某道菜在生成中，用户又去点新菜」。改造前实测（无头浏览器把第二次点菜延迟 25 秒）：

| 时刻 | 生成按钮 | 已生成菜谱 |
| --- | --- | --- |
| 点菜中（旧菜单仍在） | 仍可点 | — |
| 菜谱生成完成 | 「已生成」 | 1 |
| 新菜单落地 | 新菜单的按钮 | **0（静默丢失）** |

三个根因与对应处理：

| 根因 | 处理 |
| --- | --- |
| 「点菜中」旧菜单仍可点「生成菜谱」 | 生成按钮 `disabled` 增加 `menuLoading`，`handleGenerate` 内也兜底 return |
| 新菜单落地时 `setDishStates({})` 静默清空 | 清空前统计「已生成未入库」道数，`window.confirm` 二次确认（已入库的不算，它们在菜谱库里）；用户取消则整次点菜不发生 |
| 单槽 `abortRef` 只能取消最后一个请求 | 拆成 `menuAbortRef`（点菜）+ `dishAbortsRef: DishAborts`（按菜名登记，可全部取消）；`delete` 带实例校验，防止旧请求的 `finally` 误删同名新登记 |

**取消时机放在「新菜单确认到手」之后，而不是发请求之前**：

点菜可能失败（400/502/503/网络异常）。若在发请求前就取消在途生成，一旦点菜失败，旧菜单原样保留、但用户的在途生成已被中止并复位——用户白等十几秒还要重点一次「生成菜谱」。放到成功分支后，失败路径完全不动在途请求（实测：让点菜返回 502，在途生成照常落地为菜谱卡）。

成功分支内的顺序是 `bump 代次 → abortAll → 替换菜单并清空 dish 状态`：先推进代次保证任何已解决的结果被判过期、不写回，再取消残留请求，最后整体替换。

**能力边界（务必知晓）**：客户端 `abort` **不会中断服务端的上游 AI 调用**——`ai-client` 只有 120 秒超时，`/api/ai/menu`、`/api/ai/recipes`、`/api/ai/nutrition` 均未透传 `req.signal`（仅 `/api/ai/chat` 在流式转发途中取消 upstream reader）。因此这里的取消止损的是「用户等待与界面污染」，**不节省上游 token**。要真正止损需在 `AiCallOptions` 加 `signal` 并用 `AbortSignal.any([req.signal, timeout])` 合并，属独立改动。

纯逻辑抽在 `src/lib/dishes-regen.ts`（`DishAborts` + `countUnsavedRecipes` + `buildRegenConfirmMessage`），有单测覆盖。

### per-dish 状态机

`Record<dishName, { phase: 'idle'|'generating'|'ready', recipe?, error? }>`：

- 每道菜独立请求独立状态，**互不阻塞**（一道生成中不影响看/生成其他菜）
- 同名菜天然共用一份状态（键即菜名）→ 幂等防重复
- 单菜失败局部红字、phase 回 idle 可重试，不污染其他菜
- 菜谱生成成功后 `scrollIntoView` 自动滚到卡片（移动端卡片常在视口外，修复过「只见已生成不见内容」的体验问题）
- `menu.people` 快照作 servings：生成菜单后改输入框不影响本次结果
- 入库防抖（savedNames/savingNames）与 ChatView 同款

## 为什么这么做

| 决策 | 理由 |
| --- | --- |
| 两段式：先菜单后按需生成菜谱 | 一次生成 4~6 道完整菜谱又慢又贵（每道几百 token），用户通常只要其中两三道——成本与延迟留给真正需要的菜 |
| 菜单不含步骤（轻量 schema） | 第一段的任务是「决定买什么」，步骤是第二段的事；schema 强制轻量也让 AI 输出更快 |
| preference 自由文本而非多选框 | 自用场景下自由表达比枚举选项覆盖面广（「冰箱还有半棵白菜」也能塞进来）；实现成本低 |
| 组合语义放提示词不放 schema | 「荤素搭配是否合理」是模糊判断，zod 只能校验结构；强校验组合会误杀合法菜单 |
| preference 非字符串 → 400 | 不静默丢弃用户意图（与 Task 10 多数参数严格取向一致）；前端恒传合法字符串不受影响 |
| `<menu>` 走 extractJson 全文扫描形态 | `<recipe>` 标签优先级不认 `<menu>`，经形态 3 平衡扫描提取（实测可解并有测试） |

## 优缺点

**优点**

- 一次点击拿到结构化采购清单（合并去重，直接照单买菜）
- 库摘要防完全重复但不压制新搭配；温度 0.8 + 灵感种子提升一桌菜的多样性
- 逐菜按需生成：自由组合，无捆绑成本
- 各按钮独立 loading，多菜并行生成体验流畅

**缺点与已知边界**

- 不知道冰箱现况（冰箱场景在聊天页；两场景解耦是设计边界）
- 菜单仍可能与库中旧菜相似（仅避免完全相同；这是移除「优先已有菜」后的预期取舍）
- 大人数（>10）菜数线性外推偏多（启发式未设上限，自用可接受）
- 重置菜单时在途的「生成菜谱」请求会被**丢弃**（`src/lib/menu-epoch.ts` 的菜单代次守卫：请求返回时若菜单已被替换则不写回）——此前会按菜名写回并显示上一份菜单的菜谱

## 架构位置

```
点菜页 ──► /api/ai/menu ──► ai-client ──► 模型（库摘要注入）──► <menu> 解析+schema ──► { dishes, shopping }
   │
   └─ 逐菜 ──► /api/ai/recipes（复用结构化生成）──► RecipeCard ──入库──► /api/recipes ──► recipe-store
```

menu 接口不写盘（同 recipes AI 接口）；入库完全由用户在前端显式触发。
