# 模块：AI 对话（聊天页 + /api/ai/chat）

> 代码位置：`src/app/api/ai/chat/route.ts`（SSE 服务端）、`src/lib/sse.ts`（事件编码）、
> `src/lib/sse-client.ts`（前端解析）、`src/components/ChatView.tsx`（聊天 UI）、`src/lib/chat-history.ts`（组包）、
> `src/lib/ai-prompts.ts` 的 `CHAT_MENU_FORMAT_RULE` / `extractChatMenuJson`（清单协议与解析）
> 消费方：首页 `/`（问问AI）

## 做什么

应用的主入口：一个对话式界面，用户用自然语言说需求，AI 按两种路径响应：

1. **食材推荐清单**（默认路径）：用户列出食材（「冰箱有番茄和鸡蛋」）→ AI 按食材的自然搭配输出推荐清单（每道菜标主料+理由，理由中说明用到了哪些食材；能合并成一道菜就合并，不硬凑数量）→ 用户确认想做哪道 → 点「生成菜谱」→ 展开完整菜谱卡片 → 一键入库
2. **完整菜谱直出**：用户明确要某道菜的做法（「红烧鱼怎么做」）→ AI 直接输出完整菜谱卡片，可一键入库

与买什么模块的分工：**问问AI 有食材输入**（按现有食材自然搭配出菜，食材可合并进同一道菜），**买什么无食材输入**（按人数配一桌菜+采购清单）。

## 怎么做的

### SSE 事件协议（前后端契约，一字不差）

```
event: message   data: {"t":"<正文增量>"}          ← 结构化标签出现前的流式文本
event: recipe    data: <完整 Recipe JSON>          ← <recipe> 闭合（id/时间戳已覆写）
event: menu      data: {dishes:[{name,ingredient,reason}]}  ← <menu> 闭合（食材推荐清单）
event: error     data: {"error":"<中文>"}          ← 解析两次失败/上游异常
event: done      data: {}                          ← 收尾（error 之后照常发，不中断流）
```

### 双标签状态机（RecipeStreamSplitter）

`RecipeStreamSplitter` 同时识别 `<recipe>` 与 `<menu>`：

- text 态增量外发，尾部半截标签字面量扣留（`<rec`/`<men` 跨增量不泄漏，取两种开标签扣留长度的最大值）
- 进入先出现的标签态（indexOf 取最小位置），标签内内容缓冲不外发
- 闭合回调：`<recipe>` → onRecipeComplete、`<menu>` → onMenuComplete；首个任一标签闭合后 structSeen=true，后续正文与标签全部丢弃（协议只发首个结构化输出）
- 流中途截断在标签态：flush 快照未闭合缓冲**及标签类型**，走同一条提取路径（裸 JSON 平衡扫描可解出未闭合但完整的 JSON）

### 提示词分流（CHAT_MENU_FORMAT_RULE）

系统提示词并列多类规则，让模型按用户意图自选输出形态：

```
- 列食材想做菜 → <menu> 清单：每种主要食材都要有用途（可合并成一道菜，不为凑数硬拆），
  每道菜标注主料并在理由里说明用到的食材；
  清单阶段禁止输出 <recipe>（等用户确认）；避开最常见大路菜与对话历史重复菜
- 上一轮出过清单 + 用户说「继续/再来几道」→ 只出未推荐过的新菜（不重复为第一约束），
  未用到的食材仅作次要偏好，不强凑
- 上一轮只是文字回答 + 用户说「继续」→ 继续文字讲解，不出清单
- 「就这些/够了」→ 不出清单，简短确认
- 「开始做 X」→ 优先输出 <recipe>（未指明菜名时反问）
- 烹饪知识/闲聊 → 正常文字，不输出标签
- 明确要某道菜做法 → <recipe> 完整菜谱
- 优先级：用户明确指定菜名或要求做法时，<recipe> 优先于清单与去重
```

`extractChatMenuJson` 校验 `{dishes:[{name,ingredient,reason}]}`（三字段非空字符串，复用平衡扫描兜底）；与买什么的 menuSchema 无关（那边无 ingredient、有 category/shopping）。

每次请求在服务端注入一个随机「技法 + 风味」灵感方向（如砂锅 + 江浙），仅作为推荐/搭配时的可选参考；用户明确指定菜名时严格按菜名生成。聊天温度固定 0.7（同一端点可能直出完整菜谱，结构稳定优先），清单创意主要由反重复提示与灵感种子提供。

### 前端（ChatView）

- `readSse` 消费五类事件（message/recipe/menu/error/done）；menu 事件挂到当前 assistant 消息下方渲染清单卡片（每菜一行：菜名+主料徽标+理由，理由中说明用到的食材）
- **逐菜生成**：每道菜的「生成菜谱」按钮 → `POST /api/ai/recipes { dish }` → 该菜下方展开 RecipeCard → 入库。`dishStates` 以「消息下标:菜名」为键（跨清单同名菜互不干扰），per-dish 独立 loading 互不阻塞，失败局部红字可重试
- 入库：toDraft 剥离+savedIds/savingIds 双防抖（与原单菜谱路径完全同款）
- 组包 `buildHistory`：取最近 5 轮 + 首条用户消息锚点，过滤空文本气泡（保留空正文但有结构化输出的轮次），累计全部轮次菜名成一行摘要，末尾追加当前 user 消息；聊天记录不持久化

## 为什么这么做

| 决策 | 理由 |
| --- | --- |
| 清单先行而非直接生成完整菜谱 | 用户需求：给出 N 个食材时往往只得到 1 个菜（且未必想做）——先出清单，把「做哪道」的决定权还给用户，成本只花在确认后的那道菜上；清单按自然搭配组织，食材能合并就合并，不为了凑数硬拆 |
| 食材本身构成一道完整菜时只推荐这道 | 番茄+鸡蛋这类天然搭配若被拆成两道会显得生硬；规则要求「本身就是一道菜的完整搭配时只推荐这一道」，只有确实有多道合理搭配时才增加菜品 |
| 复用 /api/ai/recipes 生成完整菜谱 | 该接口已具备结构化输出/重试/覆写全套能力，第二段零新增服务端代码 |
| menu 与 recipe 两条协议并存而非替换 | 「红烧鱼怎么做」直出菜谱仍是高频路径；提示词按意图分流，状态机兼容两态 |
| 双标签取最先出现者进入 | 模型偶发同时输出两种标签时行为确定（取位置靠前），不会卡死或双发 |
| ingredient 字段独立于菜名 | 展示「主料：番茄、鸡蛋」徽标，理由补充说明用到的其他食材——用户可核对每种食材是否有用途 |
| SSE 而非 WebSocket | 单向推送足够；无协议升级，部署简单 |

## 优缺点

**优点**

- 食材利用率可视化：每种主要食材都有用途（可合并成一道菜），理由中说明用到了哪些食材，便于核对不遗漏
- 确认制把生成成本与用户意图对齐（只生成想做的菜）
- 双标签状态机一条流同时覆盖「推荐」与「直出」两种产品路径
- 逐菜独立生成：多道菜并行请求互不阻塞，失败不扩散

**缺点与已知边界**

- 「清单 vs 直出」的分流靠提示词遵循度（模型可能在该出清单时直出菜谱——此时行为退化为旧版，不致错）
- menu 事件数据无 id，跨清单同名菜以「消息下标:菜名」区分键
- 聊天记录不持久化，清单确认后刷新需重新描述食材（已确认的产品取舍）
- 清单条数由模型按搭配合理性决定，无硬校验（例如 4 种食材可能只出 2 道菜；食材很多时建议分批说）

## 「继续」只追加新菜（方案 A）

用户说「继续 / 再来几道」时，AI 只输出此前未推荐过的新菜。实现只在前端组包层：

- `src/lib/chat-history.ts` 的 `buildHistory` 把**全部轮次**的菜名（`menu.dishes[].name` / `recipe.name`）累计去重，汇总成一行附在**最后一条 assistant 消息**上：
  `（此前已推荐，勿重复：番茄炒蛋、青椒肉丝…）`
- **历史只发送最近 5 轮 + 首条用户消息锚点**（1 轮 = 1 条 user + 1 条 assistant）：不裁剪的话第 25 次「继续」就会撞服务端 50 条消息上限（400），累积 token 成本也随轮数线性增长；首条用户消息作为锚点保留，避免第 6 轮起模型忘记初始食材/忌口/人数
- **裁剪历史不影响摘要**：菜名摘要始终按全部轮次累计——否则早期菜名丢失，模型会在信息缺失下重复推荐（审查确认过的 Critical）
- 摘要只进请求，**界面气泡文字不变**（`buildHistory` 是纯函数，不改入参）；服务端 `/api/ai/chat` 零改动
- 上限：最多 60 个菜名、摘要总计 ≤1000 字符、单个菜名展示截断 24 字符、换行压成空格
- **超限时保留最新菜名**（近因偏差：模型最容易重复的是最近一轮的菜；保留最早 60 个会让长会话的去重失效）
- **去重键用未截断的菜名**：避免「前 24 字相同」的两道不同菜被误判为重复而漏记
- 空正文但有结构化输出的轮次也会保留菜名；若窗口内全是失败轮（无 assistant），会合成一条 assistant 承载摘要，避免去重名单彻底丢失

**实测**：连续 10 轮「继续」共 30 道菜、零重复；请求消息数在第 5 轮后稳定为 11 条（5 轮窗口 10 条 + 首条锚点 1 条），加当前消息共 12 条，远低于服务端 50 条上限。

**为什么用单行累计汇总而不是每轮附摘要**：全局去重要求完整名单，按轮裁剪会让早期菜名消失、直接导致重复推荐；单行汇总的 prompt 增量也更小（与 `systemPromptWithLibrary` 的库摘要同为单行注入）。

**提示词配套**（`CHAT_MENU_FORMAT_RULE`）：「不重复」为第一约束；未用到的食材只是次要偏好（不强行凑）；「食材覆盖」只在首轮要求；「开始做 X」→ 优先输出 `<recipe>`；明确指定菜名时 `<recipe>` 优先于清单与去重。

**已知边界**：摘要来自前端 state，刷新页面后历史清空（聊天记录本就不持久化）；超过 5 轮的中间对话不再发送给模型（首条用户消息与全部菜名名单仍保留，但更早的中间讨论会丢失）。

## 架构位置

```
ChatView ──apiFetch POST /api/ai/chat──► chat route ──aiChatStream──► 上游模型
   ▲            │ readSse                     │ 双标签状态机（recipe|menu）
   │            ├── message → 气泡增量          ├─ <recipe> ─► extractRecipeJson ─覆写─► recipe 事件
   │            ├── menu → 清单卡片             └─ <menu> ───► extractChatMenuJson ─────► menu 事件
   │            └── error/done
   └─ 确认某菜 ─► POST /api/ai/recipes ─► RecipeCard ─入库─► POST /api/recipes ─► recipe-store
```
